# Fertilizer Repeat Skip Design

## Goal

将游戏返回的 `same_fertilizer_type_already_used` 识别为“本生长季已使用该肥料”，使自动施肥后续巡查跳过对应地块，避免重复协议请求和整轮任务失败。

同时为 `fertilizer protocol event was not dispatched` 补充足够的诊断字段，以便后续确认是否由库存不足或其他运行时条件导致；本次不为该错误增加自动补肥或重试逻辑。

## Season-Scoped Skip Cache

缓存位于注入运行时的 `resources/wmpf/button.js`，只在当前程序运行期间保存。它以以下身份信息记录已施肥地块：

- 地块 ID
- 当前作物 ID（缺失时使用运行时可用的作物标识）
- 当前生长季次

批量施肥开始前，每个请求地块读取当前状态并计算身份信息：

- 命中缓存的地块不再派发施肥协议，结果标记为 `action: "skipped"` 与 `reason: "same_fertilizer_type_already_used"`。
- 未命中地块保持现有流程。
- 当地块换种、作物 ID 变化或生长季次变化时，缓存键不再命中，新作物/新季可再次施肥。
- 程序重启后缓存清空；若该作物实际已施肥，游戏回包会重新建立本季缓存。

## Response Parsing And Batch Results

现有弹窗识别继续负责发现“该化肥对同一作物仅能使用 1 次”等提示。发现后：

1. 对提示对应的请求地块写入本季跳过缓存。
2. 将该条结果标记为跳过，不计入失败。
3. 保留 `same_fertilizer_type_already_used` 作为机器可读原因，供自动化层统计与日志使用。

批次内仅部分地块已施肥时，未命中的地块仍照常执行。批次整体成功条件为：所有实际执行的地块已观察到效果，或被识别为本季已施肥；未知协议错误和未观察到施肥效果仍为失败。

自动施肥层应把“全是本季已施肥”的结果视为正常跳过，并在混合批次中继续处理成功与跳过地块，而非把 `ok: false` 的旧回包直接升级为整轮失败。

## Missing Protocol Event Diagnostics

当 `performFertilizing` 返回但没有捕获到协议事件时，保留错误 `fertilizer protocol event was not dispatched`。返回结果补充结构化诊断，至少包含：

- 请求地块与肥料类型。
- 每块地的施肥前状态（作物 ID、阶段、生长季次、成熟剩余时间）。
- 所选肥料桶及施肥前后库存计数。
- 交互管理器的当前详情/拖拽状态。
- 协议捕获尝试：是否捕获事件、事件名、派发次数、`performFertilizing` 返回值和异常。

诊断仅用于日志和后续分析，不将该错误直接归类为“肥料不足”，也不修改库存或自动填充策略。

## Scope

- 不修改前端配置项、作物识别和智能施肥选择逻辑。
- 不持久化跳过缓存，不向用户设置写入运行时施肥结果。
- 不改变其他协议错误的失败语义。

## Testing

- 已施肥回包会把对应地块写入本季缓存；下一次相同作物和季次请求不派发协议。
- 作物或季次变化后，同一地块会重新进入施肥请求。
- 混合批次中已施肥地块跳过，其它地块仍然派发并完成。
- 自动施肥把仅含 `same_fertilizer_type_already_used` 的回包当正常跳过，不报告任务失败。
- 没有派发协议事件时，结果保留原始错误并包含上述诊断字段。
