# 延迟施肥提交设计

## 目标

增加“延迟施肥”配置。关闭时，施肥维持当前的批量连续提交；开启时，仅对选中的施肥来源按地块串行提交。用户可选择种植策略、催熟策略和土地详情手动一键有机/无机肥三个范围，并设置相邻地块的提交间隔，默认 500ms。

## 范围和默认值

- 新配置默认关闭，不改变已有用户的施肥行为。
- 开关开启后，范围默认选中种植策略、催熟策略、手动执行。
- 间隔默认 500ms，由一个全局数值控制。
- “手动执行”只指土地详情页的一键有机肥和一键无机肥。
- 调度中心手动运行“自动施肥”任务不属于手动范围；它仍根据自身自动化来源归入种植策略或催熟策略。

## 状态模型

自动化配置新增以下键：

- `autoFarmFertilizerDelayedSubmitEnabled`: 是否启用延迟施肥。
- `autoFarmFertilizerDelayedSubmitScopes`: 选中的来源数组，值为 `planting`、`rush`、`manual`。
- `autoFarmFertilizerDelayedSubmitIntervalMs`: 相邻地块之间的等待毫秒数，缺失时使用 500。

前端在自动化的施肥设置区域显示开关。仅在开关开启时展示范围复选框和间隔输入；范围复选框沿用现有多选配置的交互模式。

## 调用来源

所有来源继续复用 `gameCtl.fertilizeLandsBatch`，但每次调用显式传递施肥来源和提交策略，而不在 JavaScript 侧从调用栈或地块数据猜测：

- 成功种植后的施肥传递 `planting`。
- 自动催熟和催熟联动收获传递 `rush`。
- 多季节补肥无论由自动收获还是催熟联动触发，都传递 `planting`，因为它使用种植施肥策略决定肥料模式。
- 土地详情的一键有机肥、一键无机肥传递 `manual`。

应用层将保存的延迟施肥配置解析为运行时参数。未开启或未包含当前来源时，运行时参数指定批量连续提交；开启且包含当前来源时，指定串行提交和配置的间隔。

## 运行时行为

批量连续提交保持现有修复后的行为：每块地先同步并生成独立的原生施肥事件载荷，暂存所有载荷后在同一轮中连续发送。这样活动作物的嵌套运行时数据不会从首块地复制到其他地块。

串行提交也逐块同步土地状态和调用游戏原生 `performFertilizing(landId)`，但不暂存到最后。每块地生成自己的原生事件后立即提交；在下一块地提交前等待已配置的间隔。串行模式同样禁用游戏的多地块上下文，保证每个活动作物使用自己的完整原生载荷。

若某块地生成或提交失败，保留现有的失败诊断和中断语义，不继续提交后续地块。

## 非目标

- 不改变单地块卡片的施肥操作。
- 不改变自动填充肥料。
- 不改变施肥模式、候选地块、催熟阈值或联动收获的选择逻辑。
- 不增加针对调度中心手动执行的独立范围。

## 测试

- 前端测试覆盖开关、范围和默认 500ms 间隔的可编辑渲染与保存状态。
- Go 自动化测试覆盖种植、催熟和土地详情三种来源分别传递正确的运行时提交策略。
- JavaScript VM 回归测试覆盖批量模式的“先准备、后连续发送”，以及串行模式的“生成并发送一块后再进入下一块”。
- 回归测试验证两种模式均保留每块活动作物自己的嵌套原生载荷。
