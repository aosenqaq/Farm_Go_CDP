# 好友社交排行榜分页与加载性能设计

## 目标

解决好友社交页面点击“排行榜”后长时间等待的问题。排行榜打开不再被小游戏访客刷新阻塞，后端不再为了一个日期范围或一个标签读取并返回该账号的全部历史记录。

性能目标以单账号至少 10 万条历史记录为基准：

- 已有当前会话缓存时，排行榜弹窗在 100ms 内展示已有内容；
- 无当前会话缓存时，首批 50 条本地记录在 300ms 内返回；
- 单次分页响应目标不超过 100KB；
- 小游戏运行时刷新即使达到 30 秒超时，也不能阻塞已有排行榜的查看和翻页。

## 非目标

- 本次不改变偷取、被偷和访客记录的业务含义、排序规则或账号隔离规则。
- 本次不引入预聚合排行榜表；只有基准测试证明分页和 SQL 聚合仍无法满足目标时，才单独设计预聚合方案。
- 本次不修改社交记录的导入导出行为。导出仍可读取完整的用户选定数据组，不复用排行榜分页接口。
- 本次不使用仅隐藏 DOM 行的前端假分页，因为它不能减少数据库读取、JSON 解析、Wails 序列化或传输成本。

## 当前瓶颈

当前 `FarmSocialRankings` 请求存在以下串行成本：

1. 进入社交标签时预加载今日排行榜。
2. 点击排行榜时再次请求，并固定传入 `refreshVisitors=true`。
3. 后端等待 `gameCtl.getVisitorRecords`，其运行时调用最长可等待 30 秒。
4. 偷取记录和访客记录均先按账号全量读取。
5. 每条数据库记录的 `payload_json` 都在 Go 中反序列化。
6. 日期范围在全量读取后才于 Go 内存中过滤。
7. 同一响应同时返回偷取汇总、偷取明细、被偷汇总和访客明细四组数组。
8. 前端对当前标签的完整数组再次排序和映射；偷取排行榜模式还会为每个好友重复扫描全部偷取明细。

因此，记录量增长会同时放大运行时等待、SQLite 读取、JSON 解析、Go 聚合、Wails 序列化和前端计算。

## 选定方案

采用“查询与刷新分离 + SQL 范围下推 + 按当前视图游标分页”的组合方案。

### 打开与刷新分离

- 进入社交标签时只刷新好友社交状态和排行榜偏好，不再预加载排行榜记录。
- 点击“排行榜”立即打开弹窗。
- 如果当前账号、日期范围、标签和显示模式已有会话缓存，先展示缓存；否则展示首屏加载状态并请求第一页。
- 打开排行榜不得隐式刷新小游戏访客记录。
- “刷新访客”按钮调用独立的访客刷新接口。刷新期间现有排行榜保持可读，按钮显示进行中状态。
- 访客刷新成功后，清除当前账号相关的访客页缓存，并重新请求当前视图第一页。
- 访客刷新失败时展示非阻塞错误，保留旧数据和现有翻页能力。

### 分页请求契约

排行榜查询请求包含：

- `tab`: `stolenByMe`、`stolenFromMe` 或 `visitors`；
- `viewMode`: `timeline` 或 `ranking`，访客标签固定使用 `timeline`；
- `dateRange`: `current`、`3d`、`7d`、`30d` 或 `all`；
- `cursor`: 可选的不透明游标，空值表示第一页；
- `limit`: 每页数量，默认 50，后端限制在 1 至 100；
- `now`: 仅供后端测试注入，不经 Wails JSON 暴露。

响应包含：

- 结构化状态 `ok`、`status` 和 `message`；
- 已规范化的 `tab`、`viewMode` 和 `dateRange`；
- 当前日期范围的完整汇总统计 `summary`；
- 仅属于当前标签和显示模式的 `rows`；
- `nextCursor` 和 `hasMore`；
- 可选的非阻塞提示，不承载访客刷新任务错误。

现有 `refreshVisitors` 字段从排行榜查询职责中移除。访客刷新使用单独的 Wails 方法，避免一个慢运行时调用占住本地查询响应。

`rows` 使用统一的 `RankingPageRow` 投影，避免返回互相重复的四组数组。每行包含：

- `kind`: `stealRecord`、`stealRanking`、`stolenRanking` 或 `visitorRecord`；
- `key`: 当前查询结果内稳定且唯一的行键；
- `timeMS`: 统一为毫秒时间戳；
- `displayName`: 好友或访客显示名称；
- `rank`: 仅排行榜模式使用，时间线为零并从 JSON 省略；
- `eventCount` 和 `stealCount`: 当前行适用的统计值；
- `items`: 当前偷取明细或偷取排行榜行的作物汇总，其他行返回空数组；
- `actionType` 和 `actionLabel`: 访客或被偷明细的动作信息；
- `actionTarget`: 可执行协议拉黑时使用的玩家 ID 字符串。

前端只负责把当前页结构化字段格式化为现有三列展示，不再根据完整历史重新聚合排行榜详情。

### 游标规则

时间线使用稳定的复合游标：

- 偷取记录：`occurred_at DESC, id DESC`；
- 访客及被偷记录：`occurred_at_ms DESC, id DESC`。

下一页使用严格小于上一页末项的“时间 + ID”条件。这样即使多条记录时间相同，也不会重复或遗漏。游标由 Go 统一编码和解析，前端只原样回传。

排行榜模式使用“业务统计值 + 最后发生时间 + 稳定身份键”的复合游标：

- 偷取排行榜：`steal_count DESC, event_count DESC, last_occurred_at DESC, identity_key ASC`；
- 被偷排行榜：`steal_count DESC, event_count DESC, last_time DESC, identity_key ASC`。

身份键优先使用有效的 `gid` 或 `player_id`，缺失时使用规范化后的显示名称。排行榜游标必须包含全部排序字段，以保证跨页稳定性。

游标载荷还必须包含格式版本，以及账号作用域、日期窗口、标签和显示模式的校验摘要。游标与当前请求不匹配时返回参数错误，不允许把旧账号或旧筛选条件的游标用于新查询。

## 后端设计

### 服务边界

社交服务拆分为两个互不阻塞的入口：

- 排行榜分页查询：只访问本地 SQLite，并返回当前视图的一页数据；
- 访客刷新：调用小游戏运行时，持久化新访客记录，返回刷新结果，不携带排行榜全量数据。

`App` 继续负责账号授权和当前账号作用域校验。存储接口接收明确的日期窗口、视图类型、游标和数量限制，不再向排行榜服务暴露无界的全量列表操作。

### 时间范围下推

日期范围在服务层解析一次，并下推到 SQLite：

- 偷取时间线按 `account_key` 和 `date_key`/`occurred_at` 查询；
- 访客时间线按 `account_key` 和 `occurred_at_ms` 查询；
- 非 `all` 查询必须在 SQL `WHERE` 中带时间边界；
- `all` 仍是无日期边界查询，但始终带游标和 `LIMIT`。

现有索引 `social_steal_records(account_key, date_key, occurred_at)` 和 `social_visitor_records(account_key, occurred_at_ms)` 继续用于范围查询。实现时根据 SQLite 查询计划补充包含稳定 ID 的分页索引；只有 `EXPLAIN QUERY PLAN` 证明需要时才新增索引，避免无依据的索引膨胀。

### 明细查询

时间线查询使用 `LIMIT + 1`：最多读取 `limit + 1` 条，用额外一条判断 `hasMore`，响应只返回 `limit` 条。只有当前页记录的 `payload_json` 会被反序列化。

被偷时间线在 SQL 中增加 `action_type = 1`，不再读取所有访客后于 Go 中过滤。访客时间线不增加该条件。

### 汇总与排行榜查询

汇总统计使用独立 SQL 聚合查询，在同一账号和日期窗口内计算：

- 偷取涉及人数；
- 偷取记录数；
- 被偷人数；
- 访客记录数。

排行榜模式由 SQLite 先按稳定身份键分组、排序并分页。偷取排行榜的物品详情只读取当前页身份键对应的记录，并在 Go 中单次遍历聚合，替代前端“每个好友扫描全部记录”的平方级计算。必要时增加与账号、身份键和日期相关的查询索引，但不引入常驻预聚合表。

汇总和当前页查询在同一个 SQLite 只读事务中顺序执行，使用同一日期窗口和数据库快照。任何一个必需查询失败时回滚该只读事务并返回结构化失败，不返回彼此数据版本不一致的混合结果。

## 前端设计

### 会话缓存

缓存键由当前账号作用域、`dateRange`、`tab` 和 `viewMode` 组成。缓存保存已加载的行、下一游标、是否还有下一页和汇总。

- 切换标签或模式时优先展示对应缓存，没有缓存才请求第一页；
- 切换日期范围时使用新的缓存键，不拼接旧日期范围的数据；
- 账号切换时立即清空旧账号排行榜缓存和在途请求状态；
- 数据变更操作只失效受影响的缓存，不跨账号清理。

### 请求一致性

每个查询捕获账号作用域和递增请求代次。日期、标签、模式或账号变化会在前端逻辑上取消旧请求；底层 Wails 调用无法中止时允许其结束，但结果失效。迟到响应必须在写入状态前同时验证账号作用域和请求代次。

同一缓存键只允许一个翻页请求在途。重复滚动或点击不得并发请求同一游标。翻页失败保留已有数据并允许用户重试。

### 列表交互

- 首次无缓存加载时显示列表区域加载状态，弹窗工具栏保持可操作；
- 翻页时只在列表底部显示加载状态，不清空已加载行；
- 滚动接近列表底部时请求下一页；
- `hasMore=false` 后停止观察和请求；
- 日期、标签和显示模式切换沿用现有控件，不新增额外说明文案；
- 当前页行数有限后，无需在第一阶段引入虚拟列表。若连续加载大量页后出现渲染卡顿，再基于性能测量增加虚拟化。

## 错误处理

- 无效 `tab`、`viewMode`、`dateRange`、游标或 `limit` 返回明确的参数错误，不静默使用可能导致错页的游标。
- 本地分页查询失败时，保留已显示的缓存数据；首屏无缓存时显示可重试的错误状态。
- 访客刷新超时、运行时未就绪或协议失败只影响刷新操作，不影响本地排行榜查询。
- 访客刷新成功但持久化失败时不得报告成功，也不得失效现有缓存。
- 用户切换账号后，旧账号的查询或刷新结果不得更新当前账号界面。
- 所有空结果返回空数组而不是 `nil`，保证 Wails JSON 结构稳定。

## 测试策略

### Go 服务与存储测试

- 日期范围确实进入 SQL 查询，今日、3 天、7 天、30 天和全部范围结果正确；
- 时间线首尾页、空页和 `LIMIT + 1` 的 `hasMore` 行为正确；
- 多条相同时间记录使用 ID 游标时无重复、无遗漏；
- 排行榜复合排序字段相同或部分相同时分页稳定；
- `stolenFromMe` 只读取 `action_type = 1`，`visitors` 保留全部访客动作；
- 汇总统计不受当前页大小影响；
- 响应只携带当前标签和模式的数据；
- 只反序列化当前页或当前排行榜页详情所需的 `payload_json`；
- 无效游标和参数返回结构化错误；
- 访客刷新超时不阻塞并发的本地排行榜查询；
- 账号隔离在查询、游标和刷新持久化路径上均成立。

### 前端测试

- 进入社交标签不再自动请求排行榜记录；
- 点击排行榜不传 `refreshVisitors`，弹窗先展示缓存或首屏加载状态；
- “刷新访客”调用独立接口，失败时旧列表仍存在；
- 到达底部仅请求一次正确的下一游标，并把新行追加到现有列表；
- 日期、标签和模式切换重置当前视图游标并使用独立缓存；
- 迟到响应和旧账号响应不会覆盖当前视图；
- `hasMore=false` 后不再触发翻页；
- 首屏、翻页和错误状态不改变排行榜工具栏布局。

### 性能验收

构造至少 10 万条偷取记录和 10 万条访客记录的单账号测试数据库，分别验证今日、30 天和全部范围：

- 使用 `EXPLAIN QUERY PLAN` 确认范围和游标查询命中预期索引；
- 记录首批 50 条和后续分页的查询耗时；
- 测量 Wails 返回 JSON 大小，目标小于 100KB；
- 确认点击排行榜不会发起小游戏运行时调用；
- 让访客刷新达到 30 秒超时，同时验证排行榜仍能打开、切换标签和翻页。

性能目标是验收门槛；若 10 万条基准仍无法达到 300ms，再基于查询计划和剖析结果决定是否设计预聚合表，不在本次实现中提前引入。

## 迁移与兼容

- 先增加新的分页存储方法和服务测试，再切换 Wails 排行榜返回契约和前端调用方；
- 访客刷新独立接口完成后，删除点击排行榜和旧请求中的隐式刷新路径；
- 切换完成后移除只服务于旧全量排行榜读取的接口，但保留导入导出使用的全量存储能力；
- 更新并重新生成 Wails 绑定，确保 Go 与 TypeScript 请求、响应模型一致；
- 不迁移或重写现有社交记录，现有数据库内容继续可用；
- 如查询计划需要新增索引，只通过向前兼容的数据库迁移增加，不修改已有表数据。

## 完成标准

- 排行榜打开与访客运行时刷新完全解耦；
- 日期过滤、动作类型过滤、排序和分页均在 SQLite 层完成；
- 首次请求只返回当前视图最多 50 条记录及汇总；
- 相同时间和相同统计值场景的跨页结果无重复、无遗漏；
- 账号、日期、标签和模式切换不会被迟到响应污染；
- 后端测试、前端测试、前端生产构建和 10 万条数据性能验收全部通过。
