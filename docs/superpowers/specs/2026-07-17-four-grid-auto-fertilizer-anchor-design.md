# 四格作物自动施肥锚点修复设计

## 背景

用户数据库显示，同一账号普通单块催熟成功 48 次、普通 24 块批量催熟成功 1 次，但四格作物在 2026-07-17 05:56 和 09:08 共 4 次返回 `fertilizer protocol event was not dispatched`。失败期间运行时保持健康，说明故障不是连接、总开关或普通批量施肥能力。

四格种植协议会把一个 2x2 分组按空间顺序重排，并把分组首项作为作物锚点。例如土地 `[1,2,5,6]` 的实际协议顺序为 `[5,6,1,2]`，锚点是 `5`。农场状态能为四个覆盖格提供同一个 `occupancyAnchorLandId`，但当前自动催熟仅收集各格自身 ID 并排序为 `[1,2,5,6]`；种植后施肥也继续使用原始空地列表。因此施肥运行时首先尝试非锚点 `1`，交互管理器不会产生肥料协议事件。

## 方案选择

### 采用：在 Go 自动化边界保留真实锚点

- 催熟施肥候选优先使用 `occupancyAnchorLandId`，没有该字段时回退到 `landId`/`id`，并继续去重排序。
- 种植后施肥在四格计划成功后读取 `autoPlant` 返回的 `fourGridPlantDecision.groups`。每组首项就是运行时实际派发的锚点，只向施肥接口提交这些首项。
- 普通种植或缺少四格决策信息时保留原有土地 ID，避免改变现有普通作物行为。

该方案直接修复用户要求的种植施肥和催熟施肥，复用现有运行时返回契约，修改范围小且可由 Go 单元测试完整覆盖。

### 未采用：在 `fertilizeLandsBatch` 中统一解析锚点

该方案还能覆盖手动一键施肥，但需要修改大型运行时脚本并建立额外 JavaScript 场景测试。本次问题范围是自动施肥，扩大到手动路径会增加不必要的协议回归风险。

### 未采用：为四格作物直接构造肥料协议

绕过 `performFertilizing` 会依赖未稳定记录的肥料事件名称和载荷模板。现有锚点调用已经被普通施肥成功记录验证，不需要引入新的协议实现。

## 数据流

### 种植施肥

1. `runOwnPlant` 提交包含四块土地的 `gameCtl.autoPlant`。
2. 运行时返回 `fourGridPlantDecision.groups`，每组已经按真实协议顺序排列。
3. 自动化层提取每组首个正整数作为锚点并去重。
4. `gameCtl.fertilizeLandsBatch` 只接收锚点 ID。

### 催熟施肥

1. `gameCtl.getFarmStatus` 返回锚点格和覆盖格。
2. `collectFertilizerRushLandIDs` 仍按成熟阈值判断每个状态项。
3. 合格状态项统一映射到 `occupancyAnchorLandId`，缺失时回退自身 ID。
4. 去重后的锚点列表传给 `gameCtl.fertilizeLandsBatch`，联动收获也只处理真实作物锚点。

## 错误与兼容行为

- 非四格状态没有 `occupancyAnchorLandId`，行为不变。
- 四格种植结果缺少有效分组时，保留原始土地列表，让既有错误处理继续暴露运行时异常，而不是静默跳过施肥。
- 无效、重复和非正数锚点会被过滤。
- 不修改施肥模式、成熟阈值、总开关、肥料购买或调度逻辑。

## 测试

- 验证四个覆盖格映射为一个催熟锚点。
- 验证普通催熟土地仍按自身 ID 返回。
- 验证四格种植后施肥只提交运行时分组首项。
- 验证普通种植后施肥仍提交全部已种植土地。
- 运行 `go test ./internal/farm/automation -count=1`、`go test ./... -count=1` 和前端构建。
